# 📸 Instagram Archiver Server

Мощный бэкенд-сервис для автоматического скачивания контента из Instagram и отправки его в Telegram канал. Построен на **Node.js**, **TypeScript** и **Docker**. Использует утилиту `gallery-dl` для извлечения медиа и **Redis** для управления очередью задач.

## 🚀 Возможности

*   **Автоматизация:** Скачивает фото, видео, карусели (альбомы) и Stories.
*   **Метаданные:** Извлекает описание, автора и количество лайков.
*   **Очереди задач:** Использует `BullMQ` + `Redis` для надежной обработки запросов в фоне.
*   **Telegram Bot:** Отправляет контент в канал с красивым форматированием (HTML) и группировкой альбомов.
*   **Архитектура:** Clean Architecture (SOLID) + TypeScript для легкой поддержки.
*   **Docker:** Полная изоляция окружения (Node.js + Python + gallery-dl).

## 🛠 Технический стек

*   **Runtime:** Node.js v24 LTS (Debian Slim)
*   **Language:** TypeScript
*   **Downloader:** [gallery-dl](https://github.com/mikf/gallery-dl) (Python)
*   **Queue:** BullMQ & Redis
*   **API:** Express
*   **Bot Framework:** grammY

## ⚙️ Установка и запуск

### Предварительные требования
*   [Docker](https://www.docker.com/) и Docker Compose.
*   Файл `cookies.txt` из вашего браузера (для доступа к Instagram).

### Шаг 1: Конфигурация
1.  Клонируйте репозиторий.
2.  Создайте файл `.env` в корне папки сервера:

```env
PORT=3000
AUTH_SECRET=придумай_сложный_пароль
TELEGRAM_BOT_TOKEN=твой_токен_бота
TELEGRAM_CHANNEL_ID=-1001234567890

# Настройки путей (обычно менять не нужно)
COOKIES_PATH=/app/cookies.txt
DOWNLOAD_PATH=/app/downloads

# Настройки Redis (для Docker Compose)
REDIS_HOST=redis
REDIS_PORT=6379
DOWNLOAD_TIMEOUT_MS=600000
```

`AUTH_SECRET`, `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHANNEL_ID` обязательны. Сервер проверяет настройки до подключения к Redis; запасного ключа доступа нет. `DOWNLOAD_TIMEOUT_MS` ограничивает весь проход скачивания одного поста. `SHUTDOWN_TIMEOUT_MS` задаёт срок завершения активной задачи при остановке (по умолчанию 30 секунд).

Пример для локального запуска находится в `.env.example`. В Docker путь `/app` соответствует рабочему каталогу контейнера. Боту нужны права публикации в выбранном Telegram-канале.

### Шаг 2: Запуск

Положите `cookies.txt` в корень проекта и запустите:

```sh
docker compose up --build -d
docker compose logs -f app
```

Cookies и скачанные файлы исключены из Git и Docker build context. Файл cookies подключается в контейнер только для чтения.

### Ограничения Instagram и замена cookies

Сервер извлекает медиа и метаданные за один запуск `gallery-dl`. Внутренние повторы HTTP-запросов отключены; повторами управляет очередь. Файлы карусели отправляются в порядке `num` из Instagram, а неполный набор файлов отклоняется до отправки в Telegram. Полнота проверяется по списку ID медиа, записанному перед скачиванием файлов в том же запуске: поле `count` в `gallery-dl` учитывает и фоновые музыкальные дорожки, которые сервер не скачивает. Сообщение `Missing media in post` также приводит к отклонению неполного поста. Пользовательские конфиги `gallery-dl` не загружаются, чтобы они не включили дополнительные запросы или повторы.

Настройки можно добавить в `.env`; без них применяются следующие значения:

```env
INSTAGRAM_MIN_INTERVAL_MS=60000
INSTAGRAM_REQUEST_INTERVAL_SECONDS=10
INSTAGRAM_RATE_LIMIT_COOLDOWN_MS=3600000
INSTAGRAM_COOKIES_POLL_MS=30000
```

Первое значение задаёт минимальное время между началами скачивания постов, в том числе при повторных попытках. Второе задаёт паузу между запросами извлечения данных внутри `gallery-dl` (скачивание файлов с CDN регулируется отдельно самой утилитой). Очередь обрабатывает только одну задачу одновременно, даже если запущены несколько экземпляров сервера с одним Redis и именем очереди.

При распознанном `429`, сообщении о превышении частоты или просьбе подождать скачивания переходят в общую паузу на час. Если в диагностике доступен больший `retry_after`, применяется он; обычный вывод `gallery-dl` не гарантирует наличие HTTP-заголовка `Retry-After`. При повторном ограничении пауза устанавливается снова. Замена cookies не отменяет эту паузу.

При `401`/`403`, перенаправлении на вход или challenge, сообщении о подтверждении аккаунта или автоматизации скачивания ждут новую сессию. Отсутствующие, нечитаемые и истёкшие cookies тоже приводят к ожиданию без обращений к Instagram. Во время ожидания сервер продолжает принимать ссылки; задачи и общая пауза сохраняются в Redis, а ожидание не расходует три попытки обработки. Уже скачанные задачи могут продолжать отправку в Telegram.

Для восстановления используйте привычный порядок:

```sh
docker compose stop app
# Завершите проверку аккаунта в Instagram и экспортируйте cookies после нового входа.
# Замените cookies.txt в корне проекта файлом в формате Netscape.
docker compose up -d --force-recreate app
```

При первом обновлении кода вместо последней команды выполните `docker compose up -d --build --force-recreate app`. Redis останавливать или очищать не нужно. Сервер проверяет отпечаток `sessionid`: прежний файл или изменение комментариев не снимает паузу входа. Если экспорт сохранил прежнюю `sessionid`, выполните новый вход и экспортируйте cookies ещё раз. Cookies и их значения не записываются в Redis или логи; Redis хранит только SHA-256 отпечаток заблокированной сессии.

В работающем контейнере изменение содержимого существующего файла будет замечено при следующей проверке (по умолчанию каждые 30 секунд). Атомарная замена файла может оставить bind mount на прежнем файле; `--force-recreate app` гарантирует подключение нового файла. Перезапуск с прежней сессией сохраняет паузу.

`GET /api/v1/task/:id` возвращает для отложенной Instagram-задачи `waitingReason` (`pacing`, `rate_limited`, `auth_required`, `cookies_required`) и `nextCheckAt`. Это время следующей проверки, а не обещание возобновления. Общая пауза относится к одному имени очереди: экземпляры, использующие один аккаунт, должны разделять Redis и имя очереди.

Распознавание ограничений основано на диагностике `gallery-dl`; при изменении формата ошибок оно может потребовать обновления. Неожиданный ответ Instagram с отсутствующими полями `items`, `data` или `user` также приостанавливает скачивания до новой сессии: причиной может быть как ограничение доступа, так и изменение API. Эти настройки сокращают нагрузку и останавливают известные ошибки доступа, но не гарантируют отсутствие ограничений аккаунта. Истории могут истечь во время ожидания.

Контейнер приложения работает от пользователя `node` (UID 1000). На Linux обеспечьте этому пользователю чтение `cookies.txt` и запись в каталог `downloads` на хосте. Runtime-образ содержит только production-зависимости Node.js; `gallery-dl` версии 1.32.14 установлен в отдельное Python-окружение. Версию можно изменить через build argument `GALLERY_DL_VERSION` после проверки совместимости.

Redis использует AOF (`appendfsync everysec`) и политику `noeviction`. Compose ждёт успешного healthcheck Redis перед запуском приложения. AOF уменьшает потери при перезапуске, но не исключает потерю последних записей при аварии; сохраняйте резервные копии Redis и downloads.

### API

`POST /api/v1/task` принимает JSON `{"url":"https://www.instagram.com/p/ABC/"}`. Передавайте ключ `AUTH_SECRET` в заголовке `Authorization` без префикса. Ответ `{"status":"queued","jobId":"42"}` означает приём задачи в очередь, а не завершение публикации.

Поддерживаются HTTPS-ссылки на `/p/id/`, `/reel/id/`, `/reels/id/` и конкретную историю `/stories/username/id/` на `instagram.com`, `www.instagram.com` и `m.instagram.com`. Параметры и фрагмент удаляются, адрес приводится к `www.instagram.com`. Ссылки на профиль и историю без ID отклоняются. Некорректные входные данные возвращают `400`, неверный ключ — `403`, тело запроса больше 16 КБ — `413`.

### Проверки

```sh
npm ci
npm run build
npm test
```

В GitHub Actions эти команды выполняются на Node.js 24 с Redis 7.4, затем проверяется сборка Docker-образа. Интеграционный тест очереди запускается при наличии `TEST_REDIS_HOST` (и необязательного `TEST_REDIS_PORT`, по умолчанию 6379). Он использует уникальный временный namespace Redis и удаляет только свои задачи; Instagram и Telegram заменены имитациями. Без этой переменной интеграционный тест пропускается.

### Готовность и остановка

Публичный `GET /health/live` показывает, что HTTP-процесс отвечает. `GET /health/ready` возвращает `200`, когда worker запущен и Redis доступен, иначе `503`; проверка ограничена двумя секундами. Эти endpoints не раскрывают настройки, данные задач или причины внутренних ошибок. Остальной API требует `Authorization`.

При SIGTERM/SIGINT сервер прекращает приём задач, закрывает HTTP и ждёт завершения активного worker. По истечении `SHUTDOWN_TIMEOUT_MS` процесс завершается с кодом 1; при следующем запуске сохранённый прогресс предотвращает повтор подтверждённых пакетов, а незавершённая отправка требует проверки. Если увеличиваете срок остановки, также увеличьте `stop_grace_period` в Compose (сейчас 45 секунд).

Тесты проверяют HTTP API, конфигурацию, подписи и разбиение альбомов Telegram, а также очистку каталогов задач. Они используют имитацию Telegram API и downloader; реальные Instagram, Telegram и Redis не требуются.

### Статус, повторные запросы и восстановление

`GET /api/v1/task/:id` с тем же заголовком `Authorization` возвращает статус (`pending`, `processing`, `retrying`, `completed`, `failed`), количество подтверждённо отправленных файлов (`sentFiles`), общее количество (`totalFiles`), ID сообщений Telegram и `requiresReview`. Отсутствующая или удалённая задача возвращает `404`.

Одинаковый пост получает стабильный `jobId`: ссылки `/p/` и `/reel/` на один shortcode считаются одним постом, параметры URL игнорируются. Пока запись задачи хранится в Redis, повторный POST возвращает тот же ID и не создаёт новую публикацию. Фактическое состояние существующей задачи нужно получать через GET. Завершённые задачи хранятся до суток / 1000 записей, неудачные — до 7 дней / 5000 записей. Удаление по возрасту выполняется BullMQ при завершении других задач, а не по таймеру. После удаления записи дедупликация этого поста прекращается.

`POST /api/v1/task/:id/retry` повторно ставит в очередь только неудачную задачу с безопасным состоянием доставки. Для активной, завершённой или требующей проверки задачи API возвращает `409`. Обработчик учитывает Telegram `retry_after`; однозначные ошибки прав и формата не повторяются автоматически.

Задачи с ошибкой `Gallery-dl returned incomplete or inconsistent post metadata` автоматически возвращаются в обработку при запуске сервера и затем раз в час. Повтор разрешён только до начала публикации: без отправленных файлов, ID сообщений и неопределённого результата отправки. Каждый повтор даёт новый бюджет из трёх попыток; ограничения частоты запросов и ожидание cookies продолжают действовать. Если причина сохраняется, задача проверяется снова в следующем интервале. Другие окончательные ошибки остаются для ручного повтора.

Интервал задаётся через `INSTAGRAM_METADATA_RETRY_INTERVAL_MS=3600000` в `.env`; значение `0` отключает автоматические повторы, включая проверку при запуске. Общая пауза между циклами сохраняется в Redis: несколько контейнеров и перезапуски в течение часа не обходят её. После обновления контейнера сохранившиеся задачи из лога будут подхвачены автоматически, если общий интервал уже позволяет повтор. Удалённые из Redis задачи восстановить этим способом нельзя.

Метаданные и прогресс каждого пакета сохраняются в Redis. Во время временной ошибки подтверждённо отправленные пакеты пропускаются, а скачанные файлы используются повторно. Если соединение оборвалось после начала отправки или не удалось сохранить её результат, задача завершается с `requiresReview: true`: сначала проверьте канал. Это консервативная защита от дублей, а не гарантия exactly-once доставки.

Обработка задачи и очистка находятся в `ProcessTask`. Файлы удаляются после успеха, окончательной ошибки или неопределённой доставки; при безопасном промежуточном retry сохраняются. Если после частичной публикации файлы недоступны или уже удалены, автоматическое повторное скачивание блокируется, поскольку новый набор или порядок медиа может отличаться. Ошибка очистки не вызывает повторную публикацию успешно отправленного поста. Восстановление требует сохранности Redis и тома downloads; аварийно оставшиеся каталоги пока требуют отдельной очистки.
